Just-in-time provisioning: does a customer's user who has never logged in get a Mandate principal and an `ExternalPrincipal` link created during that first login, or must somebody provision both ahead of time?

**Decision question.** `AuthenticateFederation` denies when "principal linking is absent/conflicting" (`systems/mandate/domains/federation.yaml:210`). `LinkExternalPrincipal` takes a `VerifiedContext` (`federation.yaml:147`; `core.yaml:211-223`), which only an already-authenticated Mandate caller holds. A first-time user therefore has no path through the contract as declared: it supports the provisioned mode only. The preserved source names JIT as a mode — "An authenticated, trusted external identity creates or resolves a principal during login" (`docs/sources/original-design.md:923-925`) — and leaves the choice open (`original-design.md:3399`: "JIT by default or invitation/provision only?"). This question is not one of the twelve `UNMAPPED` markers in `docs/architecture/unmapped.md`, so it had no blocker and no row in `docs/architecture/runtime-decisions.md`.

**Bounded alternatives.**

1. Provision-only: an administrator or SCIM creates the principal and the link before first login. No contract change. Per-user work for every new user, by the customer or by Mandate.
2. JIT as a new command `ProvisionExternalPrincipal(connection_id, proof)` → `ExternalPrincipalId`, gated by a `Boolean` `jit_provisioning` field on `FederationConnection`, creating the link with the existing `ExternalLinkMethod::ConfiguredFederation` (`core.yaml:169-176`). No new type, no new entity. Adapter sequence: `AuthenticateFederation`; on absent-link denial with JIT admitted, `ProvisionExternalPrincipal`, then `AuthenticateFederation` again.
3. JIT folded into `AuthenticateFederation` as a second accepted outcome. Out of bounds: every command in this system has exactly one accepted outcome and emits exactly one event, verified across all twelve domain files; a second outcome or a second event breaks the contract shape.
4. SCIM push from the customer's directory (`epic:enterprise-directory`, `story:directory-provenance`). Also zero per-user work, and the mode enterprises expect for deprovisioning. A whole subsystem; further away than 2.

Out of bounds: a new enum or struct type for the JIT rule — `crates/mandate-types/tests/inventory.rs:35,40,46,86-89,98,111` hard-asserts 110 type entries and 36 entities, and that crate is owned by `story:canonical-types`, already `implemented`.

**Proposed owner.** The `mandate.federation` contract owner — `mandate-federation` for trust and linking behaviour, `mandate-model` for the connection and link records (`docs/architecture/ownership.md:14`). The contract change itself belongs to `story:domain-runtime`, which owns `systems/mandate` and `generated`.

**Affected stories (store).** `story:domain-runtime` (the command, event and field), `story:federation-linking` (the runtime behaviour and its cases).

**Exact evidence required to clear.**

- The new command, its one accepted outcome, its one event and the `Boolean` field present in `federation.yaml`, with `ess specify validate` valid and `generated/` regenerated byte-clean, and `generated/schema/types/` still 110 and `entities/` still 36.
- A case showing a first-time user on a connection with `jit_provisioning: true` obtains a session with exactly one new principal and one new `ExternalPrincipal` whose `link_method` is `ConfiguredFederation`.
- A case showing the same user on a connection with `jit_provisioning: false` is denied with no principal or link created.
- A concurrency case showing two simultaneous first logins for one `(organization, issuer, subject)` produce one record and one declared denial, and that the denied caller's retried `AuthenticateFederation` succeeds against the surviving record (`command-obligations.md:28`; `decision-blocker:identity-uniqueness`).
- A case showing the four linking cases in `tests/security/cases.json` — `issuer-isolation`, `email-isolation`, `explicit-link`, `link-conflict` — still hold through the JIT path.
- A recorded row for the new command in `docs/architecture/command-obligations.md`.

**Operator decision, 2026-09-18.** Alternative 2. Recorded as `approval` evidence against this blocker. Not a clearance: none of the cases above exists.

## Decided 2026-09-21 — alternative 2

The operator set the session goal as the federated-login use case and stated
the JIT step in its own words:

> If no link exists and `jit_provisioning` is on, `ProvisionExternalPrincipal`
> creates the `ExternalPrincipal` and seeds the `Principal`, then login is
> retried.

That is alternative 2 in shape and in sequence: the new command gated by the
`jit_provisioning` field on `FederationConnection`, creating the link with
`ExternalLinkMethod::ConfiguredFederation`, driven by the adapter as
`AuthenticateFederation` → absent-link denial with JIT admitted →
`ProvisionExternalPrincipal` → `AuthenticateFederation`.

Measured the same day, which is why the question came due: the command exists
and no path reaches it. `crates/mandate-federation/src/authenticate.rs:118-121`
refuses `DenialClause::LinkAbsent`, and `jit_provisioning` is read from the
connection and ignored. `story:federated-jit-login` takes the adapter sequence.

Alternatives 1 and 4 are not refused by this decision. Provision-ahead remains
available, and SCIM push stays `story:directory-provenance`; this settles what
happens when neither has run and a user arrives.
